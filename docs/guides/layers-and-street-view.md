# Layers and Street View

What each Layer shows, where its data comes from, and the optional Street View panel. Back to the [README](../../README.md).

## Layers

The Layers panel over the map has a toggle for each Layer, with its own icon and colour. Next to each toggle it says how that Layer is doing: loading, how many Features it found, "None in this Search Area", or "Unavailable" if its Data Source failed or took over 8 seconds. Each Layer loads on its own, so it shows up as soon as its Data Source answers and never waits for a slower one. A Layer that fails affects nothing else.

Switching a Layer off hides its Features from the map. Its statistics stay in the Location Overview. The URL keeps the Layers you have switched off, for example `&hidden=crime`, so a bookmark or shared link opens with them hidden.

Dense Features are drawn in clusters that show how many they hold. Click a cluster, or press Enter on it, to zoom in until it splits apart. Click a single Feature to open a popup with its details and its distance from the Location. Features at exactly the same point are drawn as one, with a count, and share one popup. Each popup ends with the credits of the Data Sources its Features come from, each once, with links to them and their licences: police.uk's for a crime, planning.data.gov.uk's and Historic England's for a Planning Constraint, the provider's for a Planning Application, OpenStreetMap's for an amenity, a transport Feature or a green space, HM Land Registry's Price Paid wording for a sale and MHCLG's for its certificate, and the land data's for a Land Opportunity ([Attribution](data-sources-and-attribution.md#attribution)).

**Crime** shows the street-level crimes that data.police.uk has published for the latest month in the Search Area. The backend asks data.police.uk for its latest month, then POSTs the Search Area as a 32-corner polygon (`poly`) for that month's crimes. Once that answers, it asks for each of the 23 months before, so it can compare the last 12 months with the 12 before. Every answer is cached for 24 hours, and nothing is stored. The Location Overview counts the latest month's crimes by category, then gives the last 12 months' totals and the year-on-year change, overall and per category. Police crime locations are deliberately approximate: each crime is placed at a nearby anonymous point, and the app says so.

data.police.uk allows 15 requests a second, so every request to it waits its turn, at least 100 ms after the one before: at most 10 a second, across the whole backend. A new Search Area's 25 requests take about 2.5 seconds; a repeated one is answered from the cache at once. If data.police.uk doesn't answer for some of the 23 earlier months, or they are still waiting for a turn after 8 seconds, the Overview says the trend is incomplete and which months are missing. Its counts leave those months out and it gives no change, rather than a wrong one. Those months are asked for again next time. If the latest month fails, the Crime Layer is unavailable and the earlier months aren't asked for.

**Planning** shows the Planning Constraints that intersect the Search Area, from planning.data.gov.uk's entity data: conservation areas, listed buildings, Article 4 directions, tree preservation zones and flood zones, and the [Planning Applications](#layers) received in it in the last 3 years, from PlanIt, or PlanWire with a key. (planning.data.gov.uk's own planning-application dataset isn't used, see [ADR 0003](../../docs/architectural-decision-record/0003-planning-applications-from-a-third-party-api.md).) The backend asks for all five datasets at once, sending the Search Area as a 32-corner WKT polygon (`geometry`, `geometry_relation=intersects`) and asking only for the fields it uses. planning.data.gov.uk gives at most 500 entities a page, so if the first page says there are more, the backend asks for the rest of the pages together. Alongside the first page it asks which listed building outlines (`listed-building-outline`) the Location is inside: listed buildings themselves come only as points. Each answer is cached for 24 hours. If any of them fails, the Planning Layer is unavailable rather than counting short.

Each constraint's shape is drawn on the map, faintly filled in its type's colour and under the Search Area circle. Shapes take no clicks, so clicking inside a conservation area still moves the Location. Instead each constraint has a marker: a listed building at its own point, and a shape at the point of it nearest the Location, which is the Location itself when the Location is inside it. Its popup names it and its type, gives a listed building's grade, says whether the Location is inside it, and how far the marker is from the Location. Flood zones are mapped as many small areas, so each zone's areas are joined into one Feature, "Flood zone 2" or "Flood zone 3", and counted once. Planning Constraints whose `end-date` has passed no longer apply and are left out.

The Location Overview counts the Planning Constraints of each type in the Search Area, says whether the Location is inside any of each type, and names them: "Location is inside: Sutton in Ashfield Church and Market Place (conservation area)." planning.data.gov.uk holds only what councils have published to it, so a type with none may still apply, and whether the Location is inside a listed building is known only where the council has published outlines. The Overview says so. It credits planning.data.gov.uk under the Open Government Licence and, as planning.data.gov.uk asks for its conservation areas and listed buildings, Historic England, with the day the backend obtained them: `/api/area/planning` gives it as planning.data.gov.uk's `period`, which stays with the answer while it is cached.

The Planning Layer's **Planning Applications** (PRD FR-2.2) come from [PlanIt](https://www.planit.org.uk/api/), which gathers them from every English council's planning website (ADR 0003). They are behind one provider interface (`PlanningApplicationsProvider` in `apps/api/src/sources/planning-applications.ts`): PlanIt by default (`createPlanIt` in `apps/api/src/sources/planit.ts`), or [PlanWire](#planwire) (`createPlanWire` in `planwire.ts`). Each maps its own answers into the same Features and statistics, and gives the website and the note the Location Overview credits it with, so the frontend shows whichever the backend asked and changes nothing when you switch. The backend asks PlanIt's `/api/applics/json` for the applications in a circle around the Location as wide as the Search Area (`lat`, `lng` and `krad`, its radius in km rounded up to the metre) received in the last 1,096 days (`recent`), the newest 1,000 first (`pg_sz`, `sort=-start_date`), and only the fields it uses (`select`), which leaves out applicants' and agents' names and addresses. The request names no day, so it is the same every day, and each answer is cached for 7 days (NFR-1.4). It sends `PLANIT_USER_AGENT`, or `NOMINATIM_USER_AGENT` if that isn't set, as PlanIt asks for a User-Agent with a contact email and blocks requests without one ([Configure](getting-started.md#configure)).

PlanIt asks for at most one request a minute (NFR-1.5), so every request to it waits its turn in a queue, a minute after the one before, across the whole backend (`PLANIT_LIMITER`). A cached answer never waits. A request whose turn is free is sent at once and answered within the 8-second timeout, which starts only once its turn has come. One that has to wait joins the queue, and `/api/area/planning` answers at once with the Planning Constraints and the applications `queued`: the request carries on waiting and its answer is cached, and the frontend asks again every 5 seconds (`PLANNING_APPLICATIONS_RETRY_MS` in `useSearchArea.ts`), each time answered by our own backend, `queued` again or from the cache once the turn has come. Asking again while it waits sends nothing more to PlanIt. If PlanIt answers `429 Too Many Requests`, no request is sent to it until its `Retry-After` has passed, in seconds or as a date (a minute if it gives none), and the same request is sent again then, up to 3 times (`RATE_LIMITED_ATTEMPTS`). A request that failed after waiting is answered as unavailable for a minute (`FAILED_FOR_MS`), so asking again doesn't put it back in the queue at once. PlanIt's FAQ gives no daily limit for the API, but asks those collecting in bulk to keep to about 300 requests a day; a Search Area makes one a week.

Those received in the last 3 years (`PLANNING_APPLICATION_RULES` in `packages/shared/src/planning.ts`) inside the Search Area are shown, newest first. A record PlanIt has no location for is dropped (ADR 0003: about 9% of its records). PlanIt places an application at the point the council gave it, or else at the middle of its postcode; one without a point of the council's own (PlanIt's `other_fields` `lat` and `lng`) is marked **approximate** (about 27% of PlanIt's records, and all of Ashfield's, whose council gives none). PlanIt's `app_state` gives its status (`PLANIT_STATUSES`): Undecided, and Referred to the government or another authority, are **pending**; Permitted, and Conditions, permitted with conditions, are **approved**; Rejected is **refused**; Withdrawn is **withdrawn**; and Unresolved (no longer active with no decision, such as a split decision) and Other (not known) are **no decision, or not known**. Its type (`applicationType`) is **major** where PlanIt's `app_size` is Large, its "major, large scale developments"; **householder** where the council's own type for it says so, as PlanIt has no type of its own for them and counts them as full applications, so a council that files them as full applications, as Ashfield does, has none; and **minor** otherwise.

Each application is a Feature at its point, its marker in its status's colour: pending amber, approved green, refused red, withdrawn grey and no decision brown (`PLANNING_APPLICATION_STATUS_STYLES` in `layer-styles.ts`, each meeting WCAG AA with white). They are clustered apart from the Planning Constraints, which are drawn over them, so a listed building is never lost among dozens of applications. Its popup gives its address, its status and the day it was decided, its type and the council's own name for it, the day it was received, what it proposes, its potential impact, estimated (below), the council's reference, whether it is approximate, and links to it on the council's website and on PlanIt ("See it on planit.org.uk"). The Location Overview, below the Planning Constraints, counts the applications received in the Search Area since the first day of the 3 years, says how many are approximate, counts them by status, with each status's colour, and by type, lists the major ones with their address, proposal, status and when they were received, gives the homes they would bring, estimated (below), says where they come from and what their types mean, in the provider's own note, and credits the provider, linking to its website, with the day it was asked. If PlanIt has more than the 1,000 it gave, the Overview says so: only the newest are shown and counted. While the request waits its turn, the Overview, and a line of the Planning Layer's own under its toggle, say "Loading planning applications (rate-limited)"; if PlanIt is unavailable, they say so; every other Layer, and the Planning Constraints, load as ever, and a failure of either the constraints or the applications leaves the other shown. Once the applications have come, the Overview counts them, and the toggle counts the constraints, so the Layers panel keeps its size over the map. In NG17 1AA's 0.5 mile Search Area, PlanIt had 126 received since 11 October 2023, all approximate: 16 pending, 94 approved, 14 refused and 2 withdrawn; none householder, 124 minor and 2 major, the apartments and houses proposed at 71 High Pavement, pending, and the sports pitches at The Lawn, approved.

**Estimated housing** (PRD FR-2.2). The backend reads the new homes each Planning Application proposes from its description, by fixed rules (`proposedHomes` in `apps/api/src/sources/dwellings.ts`), the same for PlanIt's and PlanWire's: "erection of 86 dwellings" is 86, "change of use from office building to 5 flats" 5, "outline proposal for single dwelling" 1. Homes are dwellings, houses, bungalows, flats, apartments, maisonettes, cottages, studios and residential units; a house in multiple occupation, a care home, a public house, a house extension, a flat roof or an apartment block (whose homes it doesn't count) is not one. They count only where the description proposes them: after erection, construction, creation, provision, new, outline, proposed and the like, or after "to" or "into" in a change of use or conversion. Homes demolished, extended or altered, those a building is converted from, existing, former, neighbouring and replacement ones, and numbers of bedrooms, storeys or people don't count ("construction of a new 2 bedroom dwelling" is 1), nor do homes listed after a number already counted ("86 dwellings comprising 50 houses and 36 apartments" is 86). The homes proposed are counted, not less any demolished or converted. An application that only settles the details of homes already permitted, by discharging, varying or removing a condition, approving details or reserved matters, a non-material amendment or a certificate of lawful development, proposes none of its own, so a scheme isn't counted twice; nor do listed building consent, advertisements or works to trees. Homes proposed without a number ("change of use from commercial to residential") can't be counted. Each application's `estimatedHomes` is its homes, or `null`, and its `impact` a line by a fixed rule from its homes, status and type, which its popup gives: "Potential impact, estimated: 6 new homes, about 14 more residents, if it is approved and built.", "… a major housing scheme of 86 new homes, about 206 more residents, once built." from 10 homes, as planning law counts a major one, "… no new homes, as it was refused. It proposed 5 new homes.", "… it proposes homes, but its description doesn't say how many, so none are counted.", "… no new homes: it alters an existing home." for a householder application, or "… no new homes in its description." The Location Overview, below the major applications, gives "Estimated housing: N homes approved or pending in the Search Area → about N × 2.4 extra residents" (`ESTIMATED_HOUSING_RULES` in `packages/shared/src/planning.ts`), how many are approved and how many pending, from how many applications' descriptions, and how many propose homes without saying how many; `statistics.housing` gives the same. The homes of refused and withdrawn applications, and of those whose status isn't known, aren't counted. In NG17 1AA's 0.5 mile Search Area, 18 of PlanIt's 126 applications propose 58 new homes; 8 of them were refused, which leaves 50 homes approved or pending, 41 approved and 9 pending, in 16 applications: about 120 extra residents. 2 approved changes of use to residential units say no number. `dwellings.test.ts` checks the rules on every one of the 126 descriptions PlanIt recorded around NG17 1AA, word for word: the 20 that propose homes, 18 more that name homes or numbers but propose none, and that the rest propose none. The recording has no scheme of more than 7 homes, so the rules for larger ones ("up to 300 dwellings", "1,200 dwellings", a breakdown) are checked on descriptions written for the test, worded as councils word them. `estimated-housing.test.ts` checks each potential impact and the counts.

`GET /api/area/planning` gives them as `applications` (`PlanningApplications` in `packages/shared/src/planning.ts`): their `status` (`ok`, `queued` or `unavailable`), the `provider` (its `id`, `name`, `url` and `note`), the `period` of the 3 years up to the day PlanIt was asked, which a cached answer may be up to 7 days before, each as a Feature (`PlanningApplicationFeature`), and their `statistics`, whose `total` is `null` when the provider doesn't say how many it has and may have more than it gave. The Layer's `status`, `features` and `statistics` stay the Planning Constraints', and `sources` lists the provider once it has answered. Each application also has its `estimatedHomes` and `impact`, and the `statistics` their `housing` (below). The [scores](scores-highlights-and-scout-modes.md#scores) load the Planning Layer with its Planning Applications, by the same provider and the very same request, so they send PlanIt nothing more: one asked for while the same is being sent waits for its answer, rather than being told it is queued, and one asked for while it waits its turn is `queued` at once, as are the categories that need it. The Land Layer asks for them the same way, for the Planning Applications near its Land Opportunities. The Highlights load the Planning Constraints alone, with `applications: null`, as none of them reads the applications.

<a id="planwire"></a>**PlanWire** (PRD §6.17, ADR 0003) is used instead of PlanIt when `.env` sets both `PLANNING_APPLICATIONS_PROVIDER=planwire` and `PLANWIRE_API_KEY` ([Configure](getting-started.md#configure)). Nothing else changes: the same Layer, Overview, map and popups show its applications, credited to PlanWire. With `planwire` but no key, or a provider it doesn't know, the API says why as it starts (`MISSING_PLANWIRE_API_KEY` and `unknownProvider` in `apps/api/src/config.ts`), and uses PlanIt. PlanWire's [documentation](https://planwire.io/docs) and [OpenAPI document](https://planwire.io/openapi.json), read on 9 October 2026, give its radius search as `GET https://api.planwire.io/v1/applications/nearby`, with the key in an `X-API-Key` header (or `Authorization: Bearer`), and these query parameters, and no others but `include=supplier`, a pilot the app doesn't use:

| Parameter | Type | Required | Default | Limit |
|---|---|---|---|---|
| `lat` | number, WGS84 | Yes | | |
| `lng` | number, WGS84 | Yes | | |
| `radius_km` | number, kilometres | No | 1 | 50; 0.5 with a free key |
| `limit` | integer | No | 25 | 100; 10 with a free key |

It answers `{ data, meta }`: `data` is the applications, each a PlanWire Application with a `distance_m`, and `meta` gives the `lat`, `lng` and `radius_km` searched, but no total. There is no date window, page or order to ask for, unlike PlanWire's `/v1/applications` list, which has `date_from`, `date_to` and `page` but searches by council or postcode, not radius. So the backend asks for the most it gives, 100, in a circle as wide as the Search Area (`radius_km` rounded up to the metre), and keeps those received in the last 3 years (`nearbyUrl` and `mapNearby` in `planwire.ts`). The request names no day, so it is the same every day, and each answer is cached for 7 days, as PlanIt's are. If PlanWire gave 100, searched a smaller circle than it was asked (as a free key's 0.5 km is), or gave a free key's samples (which say what they leave out in an `access` object), it may have more than it gave, and the Overview says so. An application's id is PlanWire's council id and the council's reference (`ashfield/V/2025/0425`), as PlanWire's own `id` can change; it is received on its `receivedDate`, or else its `applicationDate` or `validatedDate`, and decided on its `decisionDate`. Its status comes from PlanWire's `decisionOutcome` (`PLANWIRE_OUTCOMES`): approved, refused, withdrawn and other as they are, and unknown **pending** while it has no `decision` or `decisionDate`, and other once it has one PlanWire couldn't classify. A free key's samples leave out their status and decision, so their status isn't known. PlanWire has no type or size of its own, so an application is **major** where the council's own type for it (`applicationType`) says major, as Ashfield's "Major Full" does, **householder** where it says householder, and **minor** otherwise. PlanWire doesn't say whether a council gave an application's point, so none is marked approximate, and records without `lat` and `lng` are dropped. It has no page of its own for an application, so the popup links only to the council's. PlanWire limits requests by the day (25 with a free key), resetting at midnight UTC, and by burst limits it doesn't publish, rather than one a minute as PlanIt does, so its requests never queue: a Search Area the cache can't answer is asked for at once, within the 8-second timeout. Once it answers `429 Too Many Requests`, it is asked nothing more until its `Retry-After` has passed, or else until midnight UTC, and its applications are unavailable meanwhile, though cached ones are still given. A `401` (a key it doesn't know) or `402` (a key that may not make the request) makes them unavailable and is logged with what to check. A free key gives samples only: at most 10 applications more than 30 days old, within 0.5 km, without their status, so a free key can't show a Search Area's applications.

**Amenities** shows the amenities OpenStreetMap maps in the Search Area: shops, convenience stores, cafés, restaurants, takeaways, pubs, supermarkets, gyms, hairdressers, dentists, nurseries, healthcare and offices. They come from the public Overpass API, in **one query per Search Area**: `/api/area/amenities`, `/api/area/transport` and `/api/area/green-space` arriving together share it, as `/api/area` does when it consults every source, and the answer is cached for 24 hours. The Transport and Green space Layers add their own filters to the same query rather than making queries of their own (see [Adding a Layer](developing.md#adding-a-layer)). It identifies itself with `NOMINATIM_USER_AGENT`: the public Overpass instance answers 406 Not Acceptable to Node's own User-Agent. Overpass gives up when the backend does, after 8 seconds. The query asks for 128 MiB of memory rather than Overpass's default 512 MiB (`OVERPASS_MAXSIZE_BYTES`), as the public instance runs a query only once it has the memory the query asks for, and looks only in a box reaching 100 m past its widest `around:` (`bbox`), the railway stations' 5 km, which changes nothing it finds but spares Overpass a search of every element with those tags. On 9 October 2026, asked for NG17 1AA's 0.5 mile Search Area four times each, alternately, the query without them was refused with `504 Gateway Timeout` three times and answered once in 7.6 seconds, and with them it answered every time, in 3.6 to 4.3 seconds, with the same 614 elements. Central London's 1 mile Search Area runs past 8 seconds either way, so its Layers from OpenStreetMap read "Unavailable"; asking for 32 MiB, it ran out of memory. If it runs out of time or memory it still answers, with what it had found so far and a remark saying so; the backend treats that as a failure, so the Amenities Layer reads "Unavailable" rather than counting short.

Each amenity is a Feature with its name, its type and the OpenStreetMap tag that made it that type. One mapped as an outline, such as a supermarket's building, is placed at its middle. Each has exactly one type, the first its tags match in a fixed order (`AMENITY_RULES` in `apps/api/src/sources/overpass-amenities.ts`), so a café that is also tagged as a bakery is a café. The tags are those the Business Scout Modes use for competitors (PRD FR-4.3), for example `amenity=fast_food` for a takeaway and `leisure=fitness_centre` for a gym. Healthcare is any GP, clinic, hospital, pharmacy or other `healthcare=*`; shops that aren't convenience stores, supermarkets or hairdressers are counted as "Other shops". Shops and offices tagged `vacant` are left out. The Location Overview counts the amenities of each type and names the nearest of each, with its distance. OpenStreetMap is mapped by volunteers, so some amenities may be missing or out of date, and the Overview says so.

**Schools** shows the schools open in the Search Area, from the Department for Education's Get Information about Schools register, each by its phase, with its latest Ofsted judgement (PRD FR-2.3a). It reads the England-wide files `pnpm data:prepare` prepared, not a live Data Source. Before they are prepared, it says to run `pnpm data:prepare`, the Schools score is left out of the Location Score, and every other Layer still loads (FR-6.6).

A school's phase comes from GIAS: an independent school is **independent** whatever ages it teaches; a state-funded special school, or an independent special school, is **special**; a pupil referral unit or other alternative provision is **alternative provision**; and the rest are **nursery**, **primary**, **secondary** or **all-through** by their phase of education, middle schools as GIAS deems them. Colleges, universities, children's centres, secure units and 16 to 19 academies, which Ofsted inspects as further education, are left out.

Ofsted has judged schools three ways since September 2019, so a school's latest judgement (`latestJudgement` in `apps/api/src/sources/schools.ts`) is the first of these it has in Ofsted's data:

| Latest judgement | From |
|---|---|
| Report card, no overall grade | A report card, from 10 November 2025, which grades each evaluation area (Exceptional, Strong standard, Expected standard, Needs attention or Urgent improvement) but gives no overall grade |
| Outstanding, Good, Requires improvement or Inadequate | A graded inspection's overall effectiveness, from September 2019 to August 2024 |
| Inspected, no overall grade | A graded inspection from September 2024 to November 2025, which graded only its key judgements |
| Outstanding or Good | An ungraded inspection that says the school keeps an earlier grade, "School remains Good", when its graded inspection was before September 2019 and isn't in the data |
| Inspected, no overall grade | Any other ungraded inspection, such as "Standards maintained", which names no grade |
| No Ofsted judgement here | No inspection in Ofsted's data on state-funded schools: a new school, or an independent school, which the Independent Schools Inspectorate or Ofsted inspects under another framework |

Each school is a Feature at the point GIAS gives it, in brown with a mortarboard. Its popup names it, gives its phase and type, the ages it may teach and its latest judgement, the inspection it comes from and that inspection's date, whether safeguarding was found wanting, whether Ofsted inspected the school it replaced (such as the maintained school an academy converted from), and the grades it gave each area. An independent school's says who inspects it instead.

The Location Overview gives the **nearest primary school** and the **nearest secondary school**, an all-through school counting as both, each with its distance and latest judgement, saying if it is outside the Search Area, or that there is none within 2.4 km or 6 km (`SCHOOL_SEARCH_METRES`, as far as the Schools score gives points for one, PRD §6.4). It then counts the schools of each phase in the Search Area, with their judgements, and the schools with each judgement, and credits GIAS and Ofsted under the Open Government Licence (FR-10.1a), with the dates of their data. In NG17 1AA's 0.5 mile Search Area there are four: Sutton Community Academy, 230 m away, with a report card of April 2026; Croft Primary School, 520 m away, graded in January 2025 with no overall grade; Priestsic Primary and Nursery School, Good; and Westbourne School, an independent special school the Independent Schools Inspectorate inspects.

`GET /api/area/schools` answers it, with each school as a Feature (`SchoolFeature` in `packages/shared/src/schools.ts`) and its counts and nearest schools as `statistics`. One DuckDB query over the two prepared files (`schoolsNear`) finds the schools in a box reaching 6 km from the Location, joining each to its latest inspections by its URN. `sources` lists both, GIAS with the day it made its file and Ofsted with the day its data is as at, and `/api/area` reports them and the Layer's status.

**Transport** shows the railway stations, bus stops, car parks and EV chargers OpenStreetMap maps in the Search Area, and its footpaths and cycle routes drawn as lines. It comes from the same one Overpass query as the Amenities Layer, so it adds no request of its own. That query also asks for railway stations up to 5 km from the Location (`STATION_SEARCH_METRES`, as far as the Transport score gives points for one, PRD §6.4), because most Search Areas have none: NG17 1AA's nearest, Sutton Parkway, is 1.6 km away. Only stations inside the Search Area are Features. The rest only count towards the nearest. Footpaths and cycle routes come in a second output of the same query (`out tags geom`), with each way's line as well as its point.

Each facility is a Feature with its name, its type and the OpenStreetMap tag that made it that type (`TRANSPORT_FACILITY_RULES` in `apps/api/src/sources/overpass-transport.ts`): `railway=station` or `halt`, `highway=bus_stop`, `amenity=parking` and `amenity=charging_station`. Footpaths are `highway=footway`, `path`, `bridleway` and `steps`; cycle routes are `highway=cycleway`, and paths with `bicycle=designated` (`TRANSPORT_ROUTE_RULES`). Pavements and crossings mapped separately beside and across roads (`footway=sidewalk` or `crossing`) are left out, or every street would count twice. So are cycle lanes painted on roads, private car parks and paths (`access=private` or `no`), chargers only for bikes, and miniature and heritage railways' stations. OpenStreetMap splits footpaths into many short ways, so all the footpaths in the Search Area are joined into one Feature, cut off where they cross its edge, and all the cycle routes into another, each drawn in its own colour under the Search Area circle. Each has a marker where it comes nearest the Location, and its popup gives its length in the Search Area.

The Location Overview gives the nearest railway station and its distance, saying if it is outside the Search Area, or that there is none within 5 km. It then counts the railway stations, bus stops, car parks and EV chargers in the Search Area, and gives the km of footpath and of cycle route inside it.

**Green space** shows the parks, playgrounds, nature reserves and woods OpenStreetMap maps in the Search Area, each drawn as its outline. It comes from the same one Overpass query as the Amenities and Transport Layers. That query also asks for parks up to 2 km from the Location (`PARK_SEARCH_METRES`, as far as the Green space score gives points for one, PRD §6.4), so the nearest park is found even when it is outside the Search Area. Only green spaces that reach into the Search Area are Features. Outlines come in the query's second output, with each way's line (`out tags geom`); a green space mapped as a multipolygon relation comes in a third (`out body geom`), with the lines of its member ways, which the backend joins end to end into its outer rings and holes.

Each green space is a Feature with its name, its type, the OpenStreetMap tag that made it that type (`GREEN_SPACE_RULES` in `apps/api/src/sources/overpass-green-space.ts`) and its outline: `leisure=park`, `leisure=playground`, `leisure=nature_reserve`, and `natural=wood` or `landuse=forest` for a wood. A wood that is also a nature reserve is a nature reserve. Private ones (`access=private` or `no`) are left out. Each outline is drawn faintly filled in green under the Search Area circle, whole, even where it reaches beyond the Search Area. Its marker is where it comes nearest the Location, or at the Location if the Location is inside it, so its distance is to its nearest edge, not its middle. One mapped only as a point is marked there and has no outline. Its popup names it and its type, and says where it is marked.

The Location Overview gives the nearest park and its distance, saying if it is outside the Search Area, if the Location is inside it, or that there is none within 2 km. It then counts the green spaces in the Search Area, and how many there are of each type.

**Land Coverage Area.** After the local geography, the Location Overview names the council the Location is in, found in the council boundaries `pnpm data:prepare` prepared rather than from postcodes.io, and says whether it is a Land Coverage Area: "Ashfield is a Land Coverage Area: its land data was prepared on 8 October 2026." In a council that isn't one, it says "Land data not prepared for this area" (PRD FR-2.7) and how to add it: `pnpm data:prepare --area "Mansfield"`. Below, it gives the boundaries' source and dates: "Council boundaries from ONS Open Geography, as at May 2026, prepared on 8 October 2026." Before `pnpm data:prepare` has run, it says "Not prepared. Run `pnpm data:prepare` to find the council the Location is in and prepare its land data.", and everything else loads as usual (FR-6.6). The boundaries follow the coast, so a Location on a beach may be outside every council's, which the Overview says.

In a Land Coverage Area it then gives the date of each source of its land data (FR-6.5), its datasets together where they share a source and a date: "INSPIRE Index Polygons: HM Land Registry, published on 4 October 2026", "Land use, Buildings, Roads, Water, Land Parcels: OpenStreetMap via Geofabrik, as at 8 October 2026", and planning.data.gov.uk's six datasets as at the day it wrote them. It credits the INSPIRE Index Polygons with HM Land Registry's and Ordnance Survey's statements, for the year they were published, and a link to their conditions (FR-10.2), and its postcodes, from Code-Point Open, with Ordnance Survey's, Royal Mail's and National Statistics' statements and a link to the Open Government Licence. Once they were published more than 2 months ago (`INSPIRE_OUT_OF_DATE_MONTHS` in `apps/api/src/coverage.ts`), it says so and suggests running `pnpm data:prepare` again: "Out of date. Its INSPIRE Index Polygons were published on 4 October 2026, more than 2 months ago. Run `pnpm data:prepare` again for the latest: HM Land Registry publishes them on the first Sunday of every month." A Land Coverage Area prepared before its land data was, with only its boundary, is told to run it again too.

The backend answers it in `/api/area`, as `council`: its `status`, the `council` (its ONS code and name, or `null`) and `inLandCoverageArea`. It opens the prepared GeoParquet files with DuckDB inside its own process (FR-6.3) and asks which council's boundary contains the Location (`councilAt` in `apps/api/src/sources/council-boundaries.ts`). `sources` reports ONS Open Geography with the boundaries' date as its period, or as `not-prepared` before `pnpm data:prepare`, and `unavailable` if the manifest can't be read. The files are read afresh for every request, which takes milliseconds, so a re-run of `pnpm data:prepare` shows at once, without restarting the backend. `GET /api/coverage` lists what is prepared: the England-wide datasets, and each Land Coverage Area with its own, each with its source, `sourceDate`, `preparedAt` and any `attribution` its licence requires; the Overview takes its dates from there. Each Land Coverage Area says whether it is `outOfDate`: whether its INSPIRE Index Polygons were published more than 2 months before the day the backend is asked (its `today`), or aren't prepared. Before `pnpm data:prepare` it answers `"status": "not-prepared"` with empty lists.

**Property** shows the sales in the Search Area in the last 12 months, from HM Land Registry's Price Paid Data. Price Paid is searched by postcode, not by distance (PRD FR-2.8), so the backend first asks postcodes.io for the postcodes whose middle is inside the Search Area, nearest first. postcodes.io gives at most 100 (`POSTCODES_LIMIT`). The backend then sends Price Paid's SPARQL endpoint one query for every sale in those postcodes from the same day a year ago (`pricePaidQuery` in `apps/api/src/sources/land-registry.ts`). Once those answer, the backend asks Price Paid three more queries together: every sale at those sales' addresses (`saleHistoryQuery`), and the sales in the same postcodes in the 12 months a year before and five years before. The postcodes are cached for 7 days and each Price Paid query for 24 hours. If postcodes.io fails, Price Paid isn't asked, and if either fails for the last 12 months the Property Layer is unavailable. If one of the other three queries fails, only its part is missing: the sales' histories, or one of the changes in median price. The 12 months end on the day the backend is asked, but Price Paid is published monthly, a few months behind, so the latest sales may not be in it yet. The Overview says so.

Price Paid gives a sale's postcode, not its point, so each sale is a Feature at the middle of its postcode, and every sale in one postcode is at the same point. Its marker is labelled with its price, briefly ("£173k"), or with the lowest to the highest where several sales share a postcode ("£105k–£290k"). Its popup gives each sale's price, date, property type, tenure, whether it was a new build, and its address as Price Paid records it. It then lists every sale Price Paid records at that address since 1995, newest first, each with the change in price from the sale before: "29 May 2026: £173,000, -5.7%, this sale", "6 October 2024: £183,500". Price Paid gives every sale at one address the same address, so the history query asks for the sales that share each sale's address, found through its own transaction, rather than matching addresses as text. Nothing is stored: the history is fetched live, and cached for 24 hours like any other answer.

The Location Overview counts the sales, with their median and mean price, overall and then by property type (detached, semi-detached, terraced, flat or maisonette, other), tenure and new build. Before those it gives the change in median price from the same postcodes' sales in the 12 months a year before and the 12 months five years before (`twelveMonthsBefore` in `land-registry.ts`), with each period's count and median: in NG17 1AA's 0.5 mile Search Area, +13.8% on a year before and +21.3% on five years before. A median moves with the mix of properties sold as well as with their prices, and the Overview says so. "Other property" is anything that isn't a house or a flat, such as a shop, an office or land. Its sales count towards the median and mean of every sale. If postcodes.io gave all 100 postcodes, the Search Area may have more, so the Overview says it was cut short and how far the postcodes searched reach: in NG17 1AA's 0.5 mile Search Area, 430 m of its 805 m. The Overview also shows HM Land Registry's required attribution, with the conditions Royal Mail and Ordnance Survey put on Price Paid's address data (PRD FR-10.3).

**Energy Performance Certificates** (PRD FR-2.6) are off unless `EPC_API_KEY` is set in `.env` ([Configure](getting-started.md#configure)). Without it the Property Layer is just as above: the API asks the EPC API nothing, answers `epc: null`, and nothing about EPCs, ratings, price per m² or their attribution is shown. To switch them on, sign in to MHCLG's [Get energy performance of buildings data](https://get-energy-performance-data.communities.gov.uk/) with a GOV.UK One Login account (free; it asks for an email address and a second factor), choose to use its developer API, copy the bearer token from your account page into `EPC_API_KEY`, and restart the API. Which API this is, and why, is in [OQ-8's spike](../../docs/spikes/oq-8-epc-api.md).

With the key, while Price Paid is asked for the sales, the backend asks the [Energy Performance of Buildings Data API](https://get-energy-performance-data.communities.gov.uk/api-technical-documentation) for every domestic certificate in each of the same postcodes (`/api/domestic/search?postcode=…&page_size=5000`, with the token as `Authorization: Bearer`), at most 6 requests at once (`EPC_CONCURRENCY` in `apps/api/src/sources/epc.ts`). A `404` is a postcode with none. Each home is counted once, by its latest certificate (`latestCertificates` in `packages/shared/src/epc-matching.ts`: grouped by UPRN, or by address where it has none), and the Location Overview gives how many homes in the postcodes searched have one, by band from A to G, with each band's share. Then each sale of a house or flat (not "Other property", which the register of homes doesn't cover) is matched to the certificates in its postcode with OQ-8's `matchSale`, by its flat, house number or name and street as Price Paid writes them, then by its flat and house without the street, and only where exactly one home's certificates fit. Price Paid's SPARQL endpoint gives no UPRN, so the UPRN step OQ-8 recommends first is never taken: HM Land Registry's monthly lookups from a sale to its UPRN would need downloading by `pnpm data:prepare`, which isn't built yet. The certificate current when it sold (the last registered on or before the sale, else the first after) is then asked for (`/api/certificate`), for its potential band and total floor area. Each sale's popup gives its band, the band it could reach and the day its certificate was registered ("EPC rating D, could be B (14 March 2019)"), and its floor area and price per m², its price over the floor area ("Floor area 92 m²: £1,880 per m²"), or says no EPC matched it. A floor area under 10 m² or over 1,000 m² is taken for a mistake, as the 0 m² some certificates give is, and gives no price per m² (`EPC_RULES` in `packages/shared/src/property.ts`). The Overview gives how many sales of houses and flats were matched, and the median and mean price per m² of those with a floor area. Certificates go back to 2012, and may be up to 10 years older than the sale they are matched to.

A certificate's address and postcode may be used only for energy-efficiency purposes, and are personal data, so they are used only to match a sale, inside the backend, and never answered with: a popup gives Price Paid's address, and the response gives only the certificate's number, date, bands and floor area (OGL), which `/api/area/property`'s tests check. Every EPC answer is cached in memory for 24 hours and nothing is stored. If the EPC API doesn't answer for a postcode, its homes are left out and the Overview says how many postcodes; if it answers for none, or refuses the key, the EPCs read "Unavailable" and the sales are shown as without a key; if it doesn't answer for one certificate, that sale has its band but no floor area. After a `429 Too Many Requests` the EPC API is asked nothing more until its `Retry-After`, or a minute. The Overview and each matched sale's popup credit it: "Energy Performance Certificate data from MHCLG's Get energy performance of buildings data, licensed under the Open Government Licence v3.0." (FR-10.1a).

**Land** shows the Land Opportunities in the Search Area: Land Parcels that warrant further investigation (PRD §6.6). It reads the Land Parcels `pnpm data:prepare` built for each Land Coverage Area ([above](preparing-land-data.md#prepare-land-data-optional)), not a live Data Source, and never says who owns land or whether it is for sale: every view of it says "Our data suggests this parcel warrants further investigation. It is not a statement about ownership or availability. Unregistered land still has an owner." (FR-5.7), and that INSPIRE Index Polygons cover only registered freehold titles, so land held only on a lease, or registered recently, may be missing (FR-5.8). A Land Parcel is a **Land Opportunity** when it meets the filters (FR-5.3): by default, at least 0.1 acre, 50 m or nearer a road, and not on a listed building's outline (`DEFAULT_LAND_FILTERS`). Each is drawn as its outline in its indicative **Ownership Category's** colour (FR-2.7, FR-5.4a): purple if company-owned, teal if council or public-body owned, olive if other registered, and orange if Possibly Unregistered (`OWNERSHIP_CATEGORY_COLOURS`), with a marker inside it. Without CCOD and OCOD it is olive, or orange if it is Possibly Unregistered (FR-9.3). Its popup gives its area in acres and hectares, the land it is, whether it is Possibly Unregistered and how much of it INSPIRE Index Polygons cover, the nearest road, its flood zone, the Planning Constraints it is in, whether it is on a listed building's outline, the homes it might hold, its Ownership Category, always "(indicative)", the first 10 INSPIRE Index Polygons that overlap it, how much of it each covers and each one's category, the companies' and councils' titles matched to polygons in and around it, each with its Property Address, title number, Proprietorship Category, the category it gives and how far away it is ("Metal Craft Group, Sutton-in-Ashfield (NG17 7LE): title ZZ200001, Limited Company or Public Limited Company (overseas companies data), Company-owned (indicative), 10 m away"), with HM Land Registry's statement and the date of the data, and links to HM Land Registry's [Search the register](https://www.gov.uk/search-property-information-land-registry) and [Search the index map](https://www.gov.uk/get-information-about-property-and-land/search-the-index-map), for checking who owns it (FR-5.6). Industrial, commercial and retail land use in the Search Area is drawn faintly in grey, with dashed outlines, as context (FR-2.7). The Location Overview counts the Land Opportunities, their area together, how many are Possibly Unregistered, how many are in each Ownership Category, and the homes they might hold, and says that Ownership Categories are indicative: few titles can be matched, so other registered land may well be held by a company or a council too. Without CCOD and OCOD it says they aren't prepared, so land is only Possibly Unregistered or registered, and how to add them, and the Land Coverage Area says so too; with them, it dates them and credits them as HM Land Registry's licence requires (FR-10.1a). The Development Scout Mode highlights the Layer (FR-4.3a). Nearby development activity joins with its own issue.

**Nearby land sales** (PRD FR-5.4b) are HM Land Registry's Price Paid sales of property of type "Other" within 1 mile of a Land Opportunity in the last 5 years (`NEARBY_LAND_SALES_RULES` in `packages/shared/src/land.ts`), each with its price and date, and always marked "indicative: may not be land": Price Paid's "Other" is anything that isn't a house or a flat, so land, but also shops, offices, pubs and industrial units, and the app says so. Price Paid is searched by postcode, so the backend first finds the postcodes within 1 mile of each Land Opportunity's outline in the postcodes `pnpm data:prepare` kept for its Land Coverage Area ([above](preparing-land-data.md#prepare-land-data-optional)), with DuckDB, then asks Price Paid one query for every sale of type "Other" in all of them from the same day 5 years ago (`landSalesQuery` in `apps/api/src/sources/land-registry.ts`), cached for 24 hours, and places each at the middle of its postcode, as far from each Land Opportunity as that is (`landSalesNear` in `land-sales.ts`). postcodes.io gives at most 100 postcodes, which reach only about 430 m in Sutton-in-Ashfield, so it isn't used for them. A sale Price Paid records without a postcode, as land sometimes is, or at a postcode no longer in use, can't be placed, so isn't found. Price per acre isn't given: Price Paid gives no area. Each Land Opportunity's popup counts its land sales, with their median price, and lists the newest 10 (`NEARBY_LAND_SALES_RULES.listed`) with their address and how far away they are; the Location Overview does the same for all the Land Opportunities in the Search Area, each sale as far as the nearest; both credit Price Paid as HM Land Registry requires (FR-10.3). Sutton Parkway's farm field has 76 within 1 mile since 9 October 2021, for a median of £207,000, one of them plainly land: Plot D on Sidings Road, £110,000 in February 2022, 480 m away. If Price Paid doesn't answer, they read "unavailable" and the Land Opportunities are shown as ever; for land prepared before postcodes were kept, they say to run `pnpm data:prepare` again.

**Nearby development activity** (PRD FR-5.4) is the Planning Applications within 500 m of a Land Opportunity's outline (`developmentActivityMetres` in `LAND_PARCEL_RULES`), among those received in the Search Area in the last 3 years, which the Planning Layer has: only the Search Area's are known, so none beyond its edge is counted, and the app says so. The Land Layer asks for them by the Planning Layer's very request, so PlanIt is sent nothing more, and tags each Land Opportunity with how many there are, how many are approved and how many major, the homes the approved and pending ones propose, estimated, and the approved and the major ones, nearest first, each with its distance (`nearbyPlanningApplications` in `apps/api/src/sources/nearby-applications.ts`). Its popup says "Nearby development activity: 2 Planning Applications within 500 m in the Search Area, 1 approved and 1 major, for about 120 new homes approved or pending, estimated", and lists the approved and major ones; so does the Land panel for the Land Opportunity chosen. While PlanIt's queue holds them, it says "loading planning applications (rate-limited)", and the frontend asks for the Land Layer again, as for the Planning Layer; if PlanIt fails, it says so. Across a whole Land Coverage Area they aren't looked for. OpenStreetMap's `landuse=construction` within 500 m, which FR-5.4 also names, isn't counted yet.

The **Land** tab of the side panel, beside the Overview, is the **Land panel** (FR-5.1, FR-9.1). It looks **In the Search Area** or **Across** the whole Land Coverage Area ("Across Ashfield"), lists the Land Opportunities **Largest first**, **Nearest a road first** or **Most homes first**, and offers every filter (FR-5.3, FR-5.5): the smallest and largest area in acres, the furthest from a road (10 m to 500 m, or any distance), the highest flood zone (any, up to 2, or 1 only), Possibly Unregistered only, only land of the Ownership Categories ticked (offered where CCOD and OCOD are prepared), leaving out land on a listed building's outline, and leaving out land in conservation areas, listed buildings, Article 4 directions, tree preservation zones or flood zones. Each change finds them again at once, and the map and the Layers panel show what it found. **Reset to the defaults** puts back FR-5.3's. The filters stay as they are when the Search Area changes, but aren't kept in the URL. Choose a Land Opportunity in the list, by click or by keyboard, to see its tags, its Ownership Category and the titles matched in and around it, every land sale within 1 mile of it, the INSPIRE Index Polygons that overlap it, which the map outlines with dashes as it shows the whole of it, those around it a company's or council's title is matched to in their category's colour, and the links to HM Land Registry. The first 500 are listed and mapped (`LAND_LIST_LIMIT`), and the panel says so if there are more. Across a Land Coverage Area there are too many to look for land sales near each, so the panel and their popups say that land sales are found for the Land Opportunities in the Search Area and for the one chosen. The panel credits the INSPIRE Index Polygons, CCOD and OCOD as HM Land Registry requires (FR-10.2, FR-10.1a).

Before `pnpm data:prepare`, the Layer and the panel say to run it. Where the Search Area reaches into no Land Coverage Area, the Layer's toggle, the Overview and the panel say "Land data not prepared for this area" (FR-2.7), and how to add the council: `pnpm data:prepare --area "Mansfield"`. A Search Area that reaches into a Land Coverage Area and a council that isn't one is looked at only in the Land Coverage Area, and the panel says which council's land isn't.

`GET /api/area/land` answers the Layer, with FR-5.3's defaults: each Land Opportunity as a Feature (`LandOpportunityFeature` in `packages/shared/src/land.ts`), its distance to the Location its nearest edge's, its `nearbyPlanningApplications`, and their statistics. `GET /api/land` takes the same Search Area with any of `scope` (`search-area` or `land-coverage-area`), `sort` (`area`, `road-distance` or `capacity`), `minAcres`, `maxAcres`, `maxRoadMetres` (or `any`), `maxFloodZone` (1 to 3), `possiblyUnregisteredOnly`, `excludeConstraints` (Planning Constraint types separated by commas), `excludeListedBuildingOutlines` and `ownershipCategories` (`company`, `council-or-public-body`, `other-registered` or `possibly-unregistered`, separated by commas), and answers the same way. Each Land Opportunity has its `ownershipCategory` and `matchedTitles`, and `statistics.ownershipCategories` counts them, or is `null` where CCOD and OCOD weren't prepared. In the Search Area each has its `nearbyLandSales` (`NearbyLandSales`: their `status`, the 5 years looked at, and `found`, their count, median price and the newest 10), and `statistics.nearbyLandSales` those near any of them; `sources` then lists the postcodes and Price Paid too. Across a Land Coverage Area both are `null`, and Price Paid isn't asked. Both find the councils whose boundaries the Search Area reaches into, then ask each that is a Land Coverage Area for its Land Opportunities in one DuckDB query (`landOpportunities` in `apps/api/src/sources/land.ts`), which counts them all and lists the first 500 in the order chosen. `GET /api/land/{parcelId}` gives one Land Parcel and the INSPIRE Index Polygons that overlap it, and those within 25 m a company's or council's title is matched to, with their outlines, Ownership Categories and distances, and every land sale within 1 mile of it as `nearbyLandSales`; a parcel's number is given afresh by each run of `pnpm data:prepare`. Land Parcels prepared before Ownership Categories were added read as not prepared, saying to run `pnpm data:prepare` again. On Ashfield's real land data, prepared on 9 October 2026, Ashfield has 411 Land Parcels, of which 288 meet the defaults, 18 of them Possibly Unregistered, and a search across all of it took 73 to 82 ms, and 300 ms the first time, while DuckDB opens: well inside NFR-2.4's 3 seconds. Its answer is 510 KB.

**Demographics** shows the Census 2021 output areas that reach into the Search Area, each about 125 households, shaded by a measure you choose under **Shade output areas by**, over the map's lower left (PRD FR-2.7a): its **population density**, the **median age** of its residents, its MSOA's average **household income**, or its LSOA's **deprivation** decile. It reads the England-wide files `pnpm data:prepare` prepared, not a live Data Source, so it calls nothing outside the backend. Before they are prepared, it says to run `pnpm data:prepare`, and every other Layer still loads (FR-6.6).

Each measure has five shades of one orange, lightest to darkest, with a legend that names each, drawn at the same strength as on the map. Their breaks are fixed, so a shade means the same in every Search Area: they are about where England's output areas divide into fifths (for income, its MSOAs), rounded, in `DEMOGRAPHIC_MEASURE_STYLES` in `apps/web/src/layers/demographic-measures.ts`.

| Measure | From | Shades, lightest to darkest |
|---|---|---|
| Population density | Census 2021, TS006 | Under 1,500, 1,500 to 3,500, 3,500 to 5,500, 5,500 to 8,500, 8,500 or more residents per km² |
| Median age | Census 2021, TS007A | Under 34, 34 to 39, 39 to 45, 45 to 51, 51 or more |
| Household income | ONS small area income estimates, by MSOA | Under £43,000, £43,000 to £50,000, £50,000 to £57,500, £57,500 to £67,500, £67,500 or more a year |
| Deprivation | Index of Multiple Deprivation, by LSOA | Deciles 9 to 10 (least deprived), 7 to 8, 5 to 6, 3 to 4, 1 to 2 (most deprived) |

An output area with no figure for the measure is grey, and the legend says "No figure". The shading is drawn below every other Layer's shapes, so it never hides a conservation area or a park, and choosing another measure redraws only the shading. Each output area also has a marker, where a point of it is inside the Search Area, whose popup gives all its figures as text: its residents and households, its density, median age, income and decile, and how much of it is inside the Search Area. ONS gives an output area's median age only by five-year bands, so it is found within its band, taking ages to be spread evenly through it, as ONS finds a median from bands (`medianAge` in `apps/api/src/sources/demographics.ts`), with the last band, 85 and over, taken as ten years wide.

The Location Overview estimates the Search Area's **population**, **households** and **age profile** (under 15, 15 to 24, 25 to 44, 45 to 64, and 65 and over), and the **median age** of that profile. Each output area that reaches into the Search Area counts in proportion to the share of it inside: one half inside counts half its residents. In NG17 1AA's 0.5 mile Search Area, 44 output areas reach in, 15 of them wholly, with 4,429 residents, and all 44 have 13,695, so the estimate is 9,052 residents in 3,951 households, with a median age of 40.1. The **average household income** is its MSOAs' average total annual household incomes, weighed by the households estimated to be in the Search Area in each: £38,890 a year across 5 MSOAs. The **deprivation** is the decile and rank of the LSOA the Location is in, Ashfield 005E's decile 2 of 10 (1 is the most deprived 10% of LSOAs in England), and the range of every LSOA the Search Area reaches into: deciles 1 to 10 across 14. ONS adjusts each Census table a little to protect privacy, so the age profile, from TS007A, can differ by a few residents from the population, from TS001, and the Overview says so. Below, it credits each dataset under the Open Government Licence, with the date its data dates from.

`GET /api/area/demographics` answers it, with each output area as a Feature (`OutputAreaFeature` in `packages/shared/src/demographics.ts`) and the Search Area's estimates as `statistics`. One DuckDB query over the four prepared files (`outputAreasIn` in `apps/api/src/sources/demographics.ts`) finds the output areas reaching into the Search Area, the same 64-cornered circle the map draws, and measures the share of each inside it, joining its Census figures, its MSOA's income and its LSOA's decile. The output areas are prepared in order along a Hilbert curve, in row groups of 2,048, with each one's bounds beside its outline, so DuckDB reads only the few row groups whose bounds reach the Search Area: against all of England, a Search Area takes 25 to 120 ms, 466 output areas for a 1 mile one in Islington. `sources` lists the four datasets, each with the date its data dates from as its period, and `/api/area` reports them and the Layer's status. A second query finds the median of every English MSOA's average household income in the income estimates, `householdIncome.englandMedianPounds`, which Demand compares the Search Area's with. The [scores](scores-highlights-and-scout-modes.md#scores) and the crime Highlights count per 1,000 of the Search Area's estimated residents.

## Street View

The **Street View** panel (PRD FR-2.13) is off unless `GOOGLE_MAPS_API_KEY` is set in `.env` ([Configure](getting-started.md#configure)). Without it `GET /api/street-view` answers `{ "enabled": false }`, no Street View button is shown, over the map or in any popup, and the page loads nothing from Google.

With it, a **Street View at the Location** button is over the map's top right, and each Feature's popup has a **Street View here** button. Either opens the panel over the lower half of the map, named for what it is at: "The Location", or the Feature's Layer and the first words of its marker, "Property: £173,000, Sold on 29 May 2026". Only then does the page load Google's Maps JavaScript API from `maps.googleapis.com`, once, with the key, `loading=async` and British English (`googleMapsScriptUrl` in `apps/web/src/street-view/google-maps.ts`). It asks Google's Street View service for the nearest outdoor panorama within 100 m of the point (`STREET_VIEW_RULES` in `packages/shared/src/street-view.ts`: a postcode's middle or a school's is often more than Google's default 50 m from a street), shows it facing the point, and says how far away it was taken: "From Google's nearest panorama, 20 m away, facing it." If Google has none that near, the panel says so; if Google's script can't be loaded, or Google refuses the key, it says that and what to check. Google's panorama draws its own logo, copyright and terms, which the panel never covers, and the panel credits "Street View imagery: Google Maps" beneath it, with a link to Google's terms, as Google's attribution guidelines ask (FR-10.1a). Close it with **Close Street View**; a new search closes it too, so no panorama is loaded that wasn't asked for.

Google's Street View can run only in a browser, from Google's script, with the key in the page, so it is the one thing the frontend loads from anywhere but our backend ([ADR 0001](../../docs/architectural-decision-record/0001-local-backend-between-frontend-and-data-sources.md)), as the PRD's Data Sources table has it (Maps JavaScript API). The backend calls nothing of Google's: it reads the key from `.env` as it starts, and `/api/street-view` gives it to the frontend at runtime, with `Cache-Control: no-store`, so the key is never built into the frontend or committed. It is visible to anyone who can open the page, as every Maps JavaScript API key is, so what keeps it safe is how you restrict it:

1. In the [Google Cloud console](https://console.cloud.google.com/), create a project and attach a billing account, which Google requires.
2. Enable the **Maps JavaScript API** for it, under APIs & Services.
3. Create an API key, under APIs & Services → Credentials, and restrict it: under **Application restrictions** choose **Websites** and add `http://localhost:5173/*`; under **API restrictions** choose **Restrict key** and only the Maps JavaScript API.
4. Put it in `.env` as `GOOGLE_MAPS_API_KEY`, and restart the API.
